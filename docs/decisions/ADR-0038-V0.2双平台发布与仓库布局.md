# ADR-0038：V0.2 双平台发布与仓库布局

- 状态：已接受
- 日期：2026-08-24
- 补充：ADR-0027、ADR-0035、ADR-0036、ADR-0037

## 背景

项目的 Windows 桌面端与 Android 移动端已经共享同一套 React、Rust、SQLite 领域实现，但仓库说明仍把 `app/` 描述为纯桌面软件，Android 构建文档和 APK 文件名仍带有阶段性的 “Demo”。本地发布目录也把不同平台产物混放在同一层，不利于后续开发、测试和版本发布。

用户确认将当前版本作为正式 V0.2：相较 V0.1 的早期简化界面，V0.2 完成森林玻璃 UI 重构，并增加包含三类行为工作流的 Android 移动版。

## 决定

1. 版本号统一升级为 `0.2.0`，Git 标签与 GitHub Release 使用 `v0.2.0`。
2. `app/` 继续作为共享应用工程，不复制桌面端和移动端的业务源码：
   - `app/src/` 保存共享 React 界面、移动入口与响应式样式；
   - `app/src-tauri/src/`、`migrations/` 保存共享 Rust、SQLite 与数据迁移；
   - `app/src-tauri/tauri.conf.json` 与 Windows 构建脚本负责桌面发行；
   - `app/src-tauri/gen/android/` 保存可复现的 Android Gradle 工程骨架，本机 SDK、缓存、密钥和编译输出继续忽略。
3. 本地发行物统一放入 `app/releases/`，按平台分为 `windows/` 与 `android/`。源码仓库不提交 EXE、安装包或 APK，只保留发布目录说明；二进制文件通过 GitHub Release 附件分发。
4. Android 只保留当前完整 APK，不再保留一次性行为 Demo APK。历史 Demo 仍由 ADR-0035 记录，不删除或改写历史决定。
5. V0.2 的 Windows 发布物包括 x64 离线 NSIS 安装包与便携 EXE；Android 发布物为 ARM64 APK。Android 包继续使用调试签名，发布说明必须明确它适合侧载测试、不用于应用商店，且不承诺正式签名包的无缝覆盖升级。
6. 文档按职责整理：根 README 负责项目定位和双平台入口；`app/README.md` 负责共享工程与构建；`docs/implementation/` 保存当前构建说明和历史实现记录；知识笔记、蓝图、研究记录及全部 ADR 继续保留。
7. 旧文档若只是标题或路径过时，优先重命名并更新内容，不删除仍能解释历史或方法的资料。只有重复、阶段性且已由现行文档完整替代的操作说明才可删除。

## 理由

- 共享工程能避免桌面与移动端的行为模型、数据库和导出格式分叉。
- 平台化发布目录让本地验证和 GitHub Release 附件一一对应，不会把 APK、EXE 与源码混在一起。
- 保留 ADR 与实现记录可以让后续 AI Agent 理解产品如何从 Demo 演进为完整移动版，同时现行 README 不再延续过时称呼。
- 明确 Android 调试签名边界，比把侧载包误称为商店正式包更安全。

## 影响

- package、Cargo、Tauri 与 Android 版本信息统一为 0.2.0。
- Android Gradle 工程的可复现骨架进入 Git；本机路径、构建目录、原生库和签名材料仍由 `.gitignore` 排除。
- 发布说明需要同时列出 Windows 与 Android 的平台、架构、离线边界、签名边界及 SHA-256。
- V0.1 标签和 Release 继续保留，作为早期简化版本的历史记录。

## 备选方案

### 把移动版拆成第二个仓库

会复制业务模型和数据库协议，也让跨平台修改难以同步，拒绝。

### 把所有二进制直接提交到 Git

会显著膨胀仓库并混淆源码历史，拒绝；使用 GitHub Release 附件更合适。

### 删除所有 Demo 与旧 UI 决策记录

会破坏演进脉络，也违反 ADR 不删除历史决定的协作约束，拒绝。
