# ADR-0039：Android 构建与移动端边界

- 状态：已接受
- 日期：2026-08-24
- 关联：[ADR-0035](./ADR-0035-早期主题实验与可替换资产层.md)

## 背景

当前应用以 Windows Tauri 桌面程序为主要运行形态。为了同时支持 Windows 和 Android，需要生成便携式 EXE 与可安装 APK。现有 Rust 入口已经声明 `mobile_entry_point`，SQLite 数据库位于应用本地数据目录，前端也包含窄屏布局；但仓库尚未初始化 Tauri Android 工程，也没有形成移动端构建、签名和数据迁移约定。

## 决定

1. 保留 Windows 为主要桌面平台，继续生成不带安装器的 `app.exe`。
2. 初始化 Tauri Android 工程，第一阶段只构建常见真机使用的 `aarch64` APK，不同时编译 armv7、x86 和 x86_64。
3. 第一阶段 APK 使用 Android 调试签名并支持直接安装；正式发布密钥由仓库所有者后续独立创建和长期保管，不提交到 Git。
4. Android 核心七步、一次性行为和终止旧习惯继续使用本机 SQLite，不新增账号、遥测或网络数据同步。
5. Android 最低系统版本沿用 Tauri 2 的默认 Android 7.0（SDK 24）边界；如实际依赖要求提高，另行记录决定。
6. 手机端优先保证核心行为设计、保存和读取。备份文件打开、导入导出路径、系统文件选择器和应用锁需要真机验证；若平台能力不同，不得用“已支持”掩盖限制。
7. 若后续生成商店版本或持续升级版本，改用仓库所有者独立保管的正式签名密钥，并记录包名、证书和升级策略。
8. 窄屏工作台不把返回、流程导航和两个辅助入口挤在同一行：顶栏使用两层布局，所有主要触控目标不小于 44px，并为 Android 安全区保留内边距。
9. 设计状态在手机端默认收起；用户主动展开时显示为整宽、纵向滚动的覆盖层，不再把七步轨道、方案和操作按钮排成超宽横条。主内容、状态层和方法抽屉各自保有明确的纵向滚动区域。

## 理由

- ARM64 覆盖绝大多数当前 Android 真机，能够显著减少首次下载和编译量。
- 调试签名足以完成直接安装和兼容性验证，同时避免在仓库或自动化命令中创建难以撤回的正式身份凭据。
- 数据继续放在应用私有目录，符合本项目本地优先和离线可用的核心约束。
- 先验证核心工作流，再处理文件分享、通知和商店发布，可以避免把平台移植扩大成未经验证的产品承诺。

## 影响

- 仓库会新增 `app/src-tauri/gen/android/` 生成工程。
- 本机需要 JDK、Android SDK Command-line Tools、Platform、Build-Tools、Platform-Tools、NDK 和 Rust Android ARM64 目标。
- APK 与 Windows EXE 各自拥有独立的本机数据目录，不自动同步；跨设备迁移仍需导出和导入文件。
- 调试 APK 更新时通常可以覆盖安装同一调试签名的旧版本；卸载应用会删除 Android 应用私有目录中的数据，使用前应先导出备份。
- 手机端将少展示一层常驻状态信息，换取完整的正文空间与可靠的右上角触控；状态内容仍可随时从顶栏按钮打开。

## 备选方案

### 直接生成正式签名 APK

正式密钥一旦用于发行就需要长期安全保管。当前阶段先完成应用构建，正式签名体系留到确定升级渠道时建立。

### 构建通用 APK

通用包会同时编译多种架构，首次环境下载和构建成本明显增加。个人真机测试优先 ARM64，暂不采用。

### 用网页/PWA 代替 APK

网页方案无法直接复用现有 Tauri Rust/SQLite 本地命令，也会改变离线数据边界，暂不采用。
